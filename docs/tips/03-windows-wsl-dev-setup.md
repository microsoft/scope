# Windows + WSL developer setup

This guide is the shortest path to a working Scope development environment on
Windows using WSL 2. Run repository commands from the WSL shell unless a step
explicitly says to use Windows PowerShell.

## 1. Prepare WSL and Docker

Install WSL 2 with a Linux distribution (Ubuntu is a common choice), then make
sure Docker is reachable from that distribution.

If you use Docker Desktop, enable its WSL 2 engine and integration for your
Linux distribution. From WSL, verify both Docker and Compose are available:

```bash
docker version
docker compose version
```

For better filesystem performance and fewer permission surprises, keep the
checkout in the WSL filesystem rather than under `/mnt/c`:

```bash
mkdir -p ~/src
cd ~/src
git clone https://github.com/<your-github-user>/scope.git
cd scope
git remote add upstream https://github.com/microsoft/scope.git
```

## 2. Install the repository prerequisites

Scope uses Node.js 22 and pnpm 10.29.1. After Node.js 22 is available in WSL,
enable Corepack and install the workspace dependencies:

```bash
node --version
corepack enable
pnpm --version
pnpm install
```

You also need `mkcert` for the local HTTPS authentication emulator. GitHub CLI
is required for local Copilot runs. Rust/Cargo is only required when working on
the AI gateway.

For Copilot worker development, authenticate GitHub CLI and expose the token to
the development stack:

```bash
gh auth login
export GITHUB_TOKEN="$(gh auth token)"
```

The GitHub account supplying the token must have an active GitHub Copilot
entitlement.

## 3. Start Scope

Start only the backing services when you want to run application services
natively:

```bash
pnpm docker:up:infra
```

Or start one of the Docker development stacks:

```bash
pnpm docker:dev:portal   # Portal + API development
pnpm docker:dev:copilot  # Full stack with Copilot worker + Portal
pnpm docker:dev:all      # All workers + Portal + report generator
```

## 4. Trust the local HTTPS certificate in Windows

The local authentication emulator uses a development CA generated by `mkcert`.
When Scope is running in WSL but you open the Portal in a Windows browser, the
Windows certificate store must trust that public development CA as well.

After `.certs/rootCA.pem` exists, run this in WSL to print its Windows path:

```bash
wslpath -w "$PWD/.certs/rootCA.pem"
```

Then open an interactive **Windows PowerShell** session and import that public
certificate for the current user:

```powershell
Import-Certificate -FilePath "<Windows path printed by wslpath>" -CertStoreLocation Cert:\CurrentUser\Root
```

Approve the Windows certificate confirmation, then reload the Portal. Restart
the browser if it still caches the previous trust result.

> Do not disable TLS verification. Import only `.certs/rootCA.pem`; never import
> `rootCA-key.pem` or another private key.

For more detail, see the local Entra authentication section in
[`ENV_VARIABLES.md`](../../ENV_VARIABLES.md#local-dev-setup-entra-local).

## 5. Verify the checkout

Before opening a pull request, run the normal repository checks relevant to
your change:

```bash
pnpm test
pnpm lint
```

Changes touching a worker or backing service should also run the appropriate
integration tests when credentials and Docker are available:

```bash
pnpm test:integration
```

## Troubleshooting

- **`docker` cannot connect from WSL:** verify the Docker Desktop WSL integration
  is enabled for the distribution you are using, then reopen the WSL shell.
- **The browser rejects the localhost certificate:** repeat the Windows
  certificate import above and restart the browser. Do not bypass TLS checks.
- **The repository is unusually slow under WSL:** move the checkout from a
  Windows-mounted path such as `/mnt/c/...` to the Linux filesystem, for example
  `~/src/scope`.
- **Copilot authentication fails:** verify `gh auth status`, confirm the account
  has a Copilot entitlement, and export `GITHUB_TOKEN` again in the current WSL
  shell.
